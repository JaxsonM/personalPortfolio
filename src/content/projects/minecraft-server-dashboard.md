## Overview

A public status page for our Minecraft Bedrock server, showing who's online, all-time playtime, when each player was last seen, and how hard the server is working. A Discord webhook posts in our group chat whenever someone joins.

## How it's built

### Prometheus and its sources

Prometheus works by **scraping**: every few seconds it visits a list of small web endpoints called exporters, each of which reports numbers in a simple text format, and stores them as time series. Mine has five scrape jobs:

| Source | What it measures |
|---|---|
| **Prometheus itself** | Its own health, so I'd notice if monitoring stopped working |
| **node_exporter** on the monitoring container | Memory, disk and network for the monitoring stack |
| **node_exporter** on the game server | Memory, disk and network inside the container, plus my custom player metrics (below) |
| **prometheus-pve-exporter** | CPU per container, read from the Proxmox API with a read-only token |
| **blackbox_exporter** | Whether the game port answers, tested two ways (below) |

The Proxmox exporter is a Python program, installed into its own virtual environment so its packages can't conflict with the system's. It runs as a dedicated limited user and only listens on the monitoring container's loopback address.

The last two jobs use what Prometheus calls the **multi-target exporter pattern**. Instead of running an exporter on every machine being checked, one exporter runs next to Prometheus. Prometheus connects to that exporter and passes the real target in the request, using relabeling rules to rewrite each scrape. So one Proxmox exporter can report on the host, and one blackbox_exporter can test both of the game server's addresses.

### Why CPU comes from the host

CPU usage measured inside an LXC container isn't accurate, because a container shares the host's kernel and doesn't have a true view of its own share of the processor. The Proxmox host does know each container's real usage. So CPU comes from the Proxmox API instead, through an API token limited to Proxmox's read-only auditor role, so the exporter can see everything but change nothing.

I found this out the hard way. I started with the popular community "Node Exporter Full" dashboard pointed at the game server, and it showed the CPU 96.5% busy, while Proxmox's own summary page showed the same container at about 4%. Other numbers were off too: it reported 8 CPUs, the host's thread count, instead of the container's 4, and an uptime matching the host instead of the container. Memory, on the other hand, matched Proxmox almost exactly.

I traced the panel back to its formula. "CPU busy" is calculated as 100% minus idle time, using counters node_exporter reads from `/proc/stat`. Inside an LXC container, that file is generated by LXCFS to approximate the container's view, and its idle counter most likely doesn't track real idle time, so the math concludes the CPU almost never rests. After switching to the Proxmox API, the same container read 4.9%, in line with Proxmox.

### Checking the server two ways

blackbox_exporter tests whether the game's TCP port accepts connections, twice: once at the server's address on my home network, and once through the public domain name friends use. Comparing the two narrows down problems quickly. If both fail, the server itself is down. If only the public check fails, the problem is somewhere between the internet and the server, like DNS, my public IP, or the router's port forward.

It only listens on the monitoring container's own loopback address, so it can't be used by anyone else to probe the network.

### Counting players from the server log

The Bedrock server doesn't offer metrics, but it logs every join and leave to the systemd journal. A Bash script reads those lines for the server's current run, works out who's online, and writes the result as a metrics file that node_exporter picks up through its **textfile collector**, a folder it reads extra metrics from. A systemd timer runs it every 15 seconds.

Only reading the current run matters: if the server restarts, everyone is disconnected, and a join from before the restart would otherwise look like a player who never left.

### All-time playtime and last seen

A second script turns join and leave lines into play sessions and keeps them in a permanent file, running every minute. On its first run, it went back through the journal to the server's very first start on September 23, 2026, so the totals include play from before the dashboard existed. Keeping its own file means the history survives even after the journal rotates old logs away.

The tricky part is a session that never gets a leave line, because the server stopped or crashed while someone was online. systemd gives every run of a service a unique **invocation ID** and tags each of its log lines with it. Only one run of the server can happen at a time, so when the script reads a line from a new run, any session still open from an older run must have been cut off. It closes those sessions at the last moment their run was seen, which usually lands right on systemd's "Stopped" line, since that line carries the old run's ID. Sessions from the current run are saved as still in progress.

The script also bookmarks its place in the journal with a **cursor**, and only moves the bookmark after a run succeeds. If something fails, the next run retries the same lines instead of skipping them, and running it twice over the same lines never counts a session twice.

### Publishing a public dashboard safely

The dashboard is served through my Cloudflare Tunnel like my other sites, so no ports were opened. Grafana's sign-in and settings pages live on the same hostname, so I couldn't make the whole site public. Cloudflare Access protects everything on the dashboard's hostname, and a second, more specific Access application with a Bypass policy covers only the paths the public dashboard uses: `/public-dashboards`, `/api/public`, and `/public`. When two Access applications match a request, Cloudflare applies the more specific one, so visitors can see the dashboard but can't reach anything else.

On the Grafana side, I used its **Share externally** feature, which publishes a read-only copy of one dashboard at a long, unguessable link. Visitors can view it and change the time range, but they can't edit it, see other dashboards, or run their own queries. That's how the feature is designed, so it didn't need any extra settings to lock it down. I set Grafana's `root_url` to the public address so the links it generates point to the right place, and saved the dashboard with a 30 second auto-refresh so nobody needs to reload.

The long link isn't something anyone would type, so a Cloudflare redirect rule sends the bare hostname to it. Cloudflare runs redirect rules before Access, so the redirect happens first, and the Bypass policy then lets the request through.

### Discord join notifications

A small watcher runs as its own systemd service on the game server. It follows the server's log, and when a player joins, it posts a message to our Discord through a webhook. The webhook URL acts like a password, since anyone who has it can post to the channel, so it lives in a separate config file instead of in the script, readable only by root and the watcher's own service account. That also meant moving the notifications to their own channel later was a change in Discord, with no code changes at all.

The watcher doesn't run as root. It has its own limited user, which gets permission to read the server's log through the `systemd-journal` group.

Each message is a green dot, the player's gamertag, and "joined the server." The script builds the message as JSON with `jq`, which handles escaping properly, and turns off Discord's mention parsing, so nothing in a message can ever ping the whole server.

## What broke and how I fixed it

### The 17 hour session that was really 13 minutes

After the playtime script went back through the server's whole history, the totals looked believable until I questioned the longest session: one friend apparently played for 17 hours straight. The journal told a different story. They connected at 12:09am, the server restarted at 12:22am with no disconnect logged, and they reconnected 17 hours later.

My first version only closed cut-off sessions after it had finished reading all the new lines, not at the moment a new run started. So the old session stayed open past the restart, and the next join closed it 17 hours late. I changed it to close cut-off sessions as soon as a line from a new run appears, at the last moment the old run was seen, and rebuilt the history. That friend's total dropped from 25.6 hours to 8.8. The session count stayed at 80, which confirmed only one end time had been wrong, and a second run over the same history didn't change anything, which proved it didn't double-count.

The lesson: a number that looks believable isn't the same as a number that's right. Checking the most extreme value against the raw logs caught it.

### The admin login that kept landing on the public dashboard

Once the redirect rule was in place, going to Grafana's `/login` page kept dropping me on the public dashboard instead of the admin side. Two redirects were chaining together. Because I was already signed in, Grafana sent me from `/login` to its home page at `/`, and the Cloudflare redirect rule then sent `/` to the public dashboard.

A private browser window went to the sign-in page as expected, which proved the lock itself was fine and the problem was only the redirects. The fix was simply using `/dashboards` as my way into the admin side.

### Installing on the hypervisor by mistake

I installed the Proxmox exporter and it worked, but on the Proxmox host instead of the monitoring container. I noticed from the shell prompt, and the Python version in the installed file names confirmed it. I removed it from the host and reinstalled it in the container, because anything running on the hypervisor runs as root on the machine every other guest depends on, and I want that machine to stay as minimal as possible.

### Smaller Grafana lessons

- **A table that only showed one player.** A table panel fed by a time series query showed one row. The query's format needed to be set to Table instead of Time series, so each player became a row.
- **Gamertags that turned into NaN.** I set a unit on the whole panel, so Grafana tried to treat the gamertag column as a number too. Moving the unit to a per-field override on just the numeric columns fixed it.
- **Building Who's Online with nobody online.** It's hard to build a panel for online players when nobody's playing, so I wrote some test data into the metrics file to see how the panel would look.
- **A memory graph that looked jumpy.** Memory seemed to swing up and down until I looked at the axis: it was auto-scaling from 32.00% to 32.16%. The line was nearly flat. Always read the axis before reading the shape.

## Reading the graphs

One thing I learned from watching the dashboard: on the Server Resources panel, CPU jumps up and down with player activity, but memory stays nearly flat all day, even when everyone logs off.

The two measure different things. CPU is the work being done right now. Memory is what the server is holding onto. The game server loads the world into memory and keeps it there, and like most programs, it rarely hands memory back to the system even after it stops using it, because asking for it again later is slow. So a flat memory line is healthy. The patterns worth alerting on are memory that climbs for days without leveling off (a memory leak), or memory approaching its limit.
